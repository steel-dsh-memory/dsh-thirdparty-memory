一、这次改了什么
----------------
1) 存储层 JSON → SQLite（node:sqlite，零运行时依赖，WAL）
   - dataFile 配置仍可写 .json；实际库是同目录同名的 .sqlite（memory.json → memory.sqlite）。
   - 首次读取做一次性「复制式迁移」：先复制 memory.json 为
     memory.json.bak_pre_sqlite_<ISO时间戳>，再导入新库；原 JSON 不写、不删、不改名。
   - 运行时没有 node:sqlite（Node < 22.5）自动回退 JSON，功能不缩水（向量检索除外）。

2) 本地向量索引（零依赖、不联网）
   - 字符 1/2/3-gram + 拉丁词 → FNV-1a 哈希到 256 维 → TF 加权 → L2 归一 →
     Float32 BLOB 存 SQLite 的 vectors 表。
   - 检索得分 = 关键词得分 + round(cos × 12 × vectorWeight)，低于 vectorMinCos 不计分。
   - 诚实口径：这是「字面相近」（同字/同词/语序变化），不是同义词级语义。
   - 配置：vector（true/false）、vectorWeight（默认 1）、vectorMinCos（默认 0.3）。

3) 更新不碰记忆文件（硬约束）
   - 默认数据目录移出插件目录：Windows 为 %APPDATA%\dsh-thirdparty-memory\，
     可用 DSH_THIRDPARTY_MEMORY_HOME 覆盖。
   - 老版本放在插件目录 data\memory.json 的数据，只作「只读迁移来源」，原文件保留。
   - attach.ps1 不传 -DataFile 时保留已有 dataFile 行（以前会删掉，等于悄悄换记忆文件）。
   - 管理器 exe 的「切换存储目录」会连 memory.sqlite、-wal、-shm 一起复制。

4) P0 崩溃修复：Store/MSIX 版 DSH Desktop 安装后重启即崩
   - 根因：profile 的 package.json 被写成 UTF-8 with BOM；宿主 readProfileManifest
     直接 JSON.parse 不剥 BOM → SyntaxError: Unexpected token '\uFEFF' → 退出码 1 →
     连崩 3 次后宿主停止自动重启。
   - 修复：attach.ps1 与管理器 exe 全部无 BOM 写入；读取容错 BOM；
     新增 attach.ps1 -Repair（先备份 package.json 为 .bak_bom_<时间戳>，再剥 BOM）。

五、生效方式（重要）
--------------------
1) 记忆数据不在这次做主动迁移：当前仍在运行的旧插件进程还会写 JSON，
   现在迁移会让之后写入丢失。重启 DSH 后，新插件第一次读取时自动迁移并留备份。
2) 已手动停掉旧的记忆页进程（127.5.0.1:7891），重启 DSH 后新插件会自动拉起。
3) 重启后到记忆页确认：设置页应显示 SQLite 库路径、向量条数；数据条数与迁移前一致。
4) Store 版 DSH Desktop 需要点控制器的「重新启动 Harness」；profile 清单已修好。
